# 长连接修复方案 · Grill 决策记录

> 用途：逐条记录用户的直接决策，供后续开发与复查。未确认的写「待决」，不替用户默认。
> 规则：一次一题；不推测用户意图；矛盾点当场指出。

## 一、问题定义（实测锁定）

- opencode.ai 有 4 个 A 记录：.20/.21/.22/.23；**.20 与 .22 恒黑洞**（TCP 443 建连超时）。
- 短时观测内 IP 集合稳定，**变化的是 DNS 返回顺序**（20 次解析出现 12 种序列）→ 间歇性命中黑洞。
- 另有 4 个 AAAA（IPv6）记录 2606:4700:78::90:0:140~143（用户决定不使用 IPv6）。
- 命中黑洞：Windows SYN 重传耗尽约 21 秒；可用 IP 仅 0.19 秒 + TLS 0.34 秒。
- DSH 走 Node 内置 fetch（undici 7.29.1）：默认 connectTimeout=10s、keepAliveTimeout≈3s。
- DSH 的 opencode-go 配置无任何传输层参数；真实请求间隔 p50=12.98s、92.8%>4s。

## 二、方案架构（已定）

做一个 **DSH 插件**（host + client 两半区），在 host 侧接管 undici 的 DNS 解析，
对 opencode.ai 做 TLS 探测，维护内存黑名单，过滤掉黑洞 IP。

## 三、已确认决策

| 编号 | 决策 | 依据 / 用户原话 |
|---|---|---|
| D1 | 不采用本地代理（连接保管器），仅作降级备选 | 「有点笨，不喜欢这种不优雅的方法」 |
| D2 | 黑名单落在**插件层（DSH 进程内 DNS 过滤）**，不用系统 hosts | 「黑名单就是要配合我们的自动探测」 |
| D3 | 探测超时 **6~10 秒**（不用 2 秒） | 「插件给别人用…2 秒万一人家网不好就出问题」 |
| D4 | 黑名单**不持久化**，仅存活于本次 DSH 运行期 | 「免得后续出问题，关掉就自动丢弃」 |
| D5 | 「优雅」= 代码简洁 + 与 DSH 相性好 + 不暴力爆改 + 不反复打扰远端 | 「老是 ping 别人不礼貌」 |
| D6 | **不做保活**，接受每次 0.53s 建连成本 | 「C，这种时间是可以接受的」 |
| D7 | `connect timeout` 保持**默认 10 秒** | 「10 秒也连不上那也别用了」 |
| D8 | **异步探测**，不阻塞 DSH 启动 | 选 B |
| D9 | 探测全失败 → 先不过滤，**1 分钟后再探，仍失败 2 分钟后再探，第三次失败则放弃** | 用户指定 |
| D10 | 借鉴 mac-tunnel 的 GUI 小状态显示器，点击可刷新 | 「可以抄一下」 |
| D11 | 检测到用户配置了代理 → **插件自动禁用**并在面板提示 | 选 A（宁可不生效也不破坏代理） |
| D12 | 探测做到 **TCP + 完整 TLS 握手**（验证证书链），不发 HTTP 请求 | 「B 更符合不自信采述；ping 和请求要分开」 |
| D13 | 面板先做 **C 档（每 IP 探测结果与耗时）**，后续加 A/B/C 切换设置项 | 用户指定 |
| D14 | 插件**只针对 opencode.ai**，不做通用 IP 优选 | 「不能保证每家厂商的服务器问题都一样」 |
| D15 | 交付：**GitHub 开源（Apache-2.0）+ npm 发布 + tgz** | 用户指定 |
| D16 | 面板点击 = **先重探，再按重探结果重建黑名单** | 用户指定 |
| D17 | **二元判定**：TLS 握手成功=可用，超时/失败=黑洞；慢 IP 不剔除 | 「可以为慢网络妥协，但不能将就他们」 |
| D18 | 面板**显示上次探测时间**（host 记录时间戳，client 每分钟刷新换算） | 用户指定 |
| D19 | 探测超时 **固定 10 秒**（与运行时 connect timeout 同口径，避免误杀） | 选 B |
| D20 | 验收三条全要（抓包 / 开关对比 / 强制注入黑洞），测试环节做足 | 「测试环节越完善越好」 |
| D21 | **黑名单软 TTL（A）+ 探测失败二次确认（B）**：误判最多存活 TTL，连续两次失败才判黑洞 | 用户观察「IP 动不动就变成黑洞」后追加 |
| D21.1 | TTL 默认 **5 分钟**（实测波动尺度 3~4 分钟，取余量）；二次确认间隔 2 秒 | Lead 依采样数据定 |

## 四、已被事实推翻的初始设想

| 初始设想 | 结论 |
|---|---|
| 「不知道 IP 轮换频率，所以每次启动探测一次」 | 理由错：IP 集合不轮换，变的是解析顺序；黑名单过滤本就不需要知道轮换频率 |
| 「花半分钟探测」 | 不必：并发探测，总耗时约等于超时值 |
| 「每隔 3 秒 ping 保活」 | 负收益：只值 0.53s/次，却要每天数万次请求，且违反 D5 |
| 「启动探测一批固定 IP」 | 漏洞：第一次请求的解析集合未必与探测时一致 → 已改为**动态发现 + 按需探测** |

## 五、待决问题

1. **探测超时的确切值**（6 / 8 / 10 秒，或可配置）；
2. DNS 列表缓存策略（是否跟随 TTL 59s）；
3. 运行期发现**新 IP** 时的探测策略（是否也 1/2 分钟重试）；
4. 插件自身异常时的隔离要求（不得拖垮 DSH）；
5. 验收标准（怎么判定插件真的生效了）；
6. IPv6 的禁用方式（`family: 4`）。

## 六、插件机制研究结论（供实现用）

- 包结构：`type:module` + `main` + `exports` + `dsh.bundle.patch` + `dsh.client{platform,inject}`；
- `cordis.patch.yml` 一行 `insert: [{id,name}]`；profile 的 package.json 依赖 + `dsh.profile.bundles` 注册；
- Host：`export name/inject/apply(ctx, rawConfig)`；`ctx.inject([...],cb)`；`ctx.effect(disposer)`；`ctx.on('dispose')`；
- Host 可用 `webServer.register({kind:'exact',path,handler})` 开状态路由；
- Client：`window.__ModuleLoader__.load({id,factory})` + `ctx.slots.inject/register` + `exports.inject=['slots']`；
- 坑：apply 不可返回业务对象（Invalid effect）；加载器按包名缓存模块（改代码要改 config 或重启）；未 inject 的服务访问即抛。
